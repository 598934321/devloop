# /devloop — 第一性原理迭代开发

对用户给出的开发需求执行下面的迭代闭环，直到子代理黑盒审查完成度达到 100%，然后清理并汇报。

需求 = 调用时传入的参数；若未带参数，先向用户问清需求再开始。

## 硬约束（全程有效，不得违反）

- **禁止直接上线生产端**：任何把代码/服务发布到生产环境的命令、脚本、CI 触发一律不执行。本流程的部署终点是 staging 或本地环境；生产上线永远留给用户人工决策
- **部署命令硬校验**：执行任何部署/发布类命令前，必须先解析并打印完整命令与目标环境，确认目标非生产；命令行或脚本内容出现生产信号（prod / production / --promote / release / 生产）时一律拒绝执行，本轮标注"待人工部署"并继续往下走本地验证
- **未推送的提交不部署到远端**：部署到 staging 的必须是已 commit 且已 push 的精确 SHA
- **遵循项目自身规范**：先读项目规则文件（AGENTS.md / CLAUDE.md / CONTRIBUTING / README / docs 下的运维文档），版本号格式、commit 规范、测试命令、部署脚本一律以项目为准；项目无规定时，commit message 至少写清"改了什么、为什么"
- **审查子代理只审查不改代码**：所有修复由主会话完成
- 每轮迭代维护一份台账：版本号（如有）、git SHA、改动摘要、审查完成度、部署状态

## 步骤 0：需求澄清与计划

1. 用第一性原理复述需求：要解决的**本质问题**是什么、输入/输出、成功判据、边界条件、必须成立的不变量。不接受表象描述，追问到不可再分。
2. 需求有歧义或存在多种合理解法 → 先问用户，再动手。
3. 用你所在 agent 的任务清单工具建立任务清单（Devin: `todo_write`；Claude Code: `TaskCreate`/`TodoWrite`；其他: 等价物），覆盖开发 / 验证 / 部署 / 审查 / 各轮修复。

## 步骤 1：第一性原理开发（每轮迭代入口）

1. 从根本目标推导**最小正确实现**：先读相关代码和既有约定，不臆造架构、不打补丁式修表象、不引入与问题无关的复杂度。
2. 实现改动，遵循项目代码风格与架构边界。
3. 本地验证拿证据：用项目自身的 build / lint / test 命令或针对性脚本验证；验证不过就修好再往下走。
4. 若项目有版本号规范（如 package.json version + 递增规则），按规范递增。

## 步骤 2：提交与部署判定

1. `git status` + `git diff` + `git log` 确认改动范围与项目 commit 风格；只提交本轮相关文件（不要把无关的未跟踪文件捎进去）。
2. commit → push → `SHA=$(git rev-parse HEAD)` 记录进台账。
3. 识别部署通道：查项目的部署脚本 / CI 配置 / 运维文档，分清哪条命令去 staging、哪条去生产。
4. 部署分支判定：
   - **涉及服务端**（API 路由、服务端库、DB/schema/数据、鉴权、中间件、部署配置等）且项目有 staging → 部署到 staging，记录访问地址与验证点
   - **纯前端/样式/文案/文档**，或项目无 staging → 本地部署验证（build + dev server 实测），台账注明"本地验证"
   - **分不清哪条命令会上生产** → 不猜、不试，本地验证并标注"待人工部署"，同时向用户说明
5. 任何情况下都不执行生产发布；staging 验证通过即本轮部署终点。

## 步骤 3：子代理黑盒对抗性审查

用你所在 agent 的子代理机制启动**前台**审查子代理（等报告返回后再继续），要求它能跑 shell 命令做实际探测：

- Devin：`run_subagent`，`profile: subagent_general`
- Claude Code：`Task` 工具，`subagent_type: general-purpose`
- Kimi Code：`Agent` 工具，`subagent_type: "coder"`
- 其他 agent：等价的通用子代理机制；若无子代理能力，退化为主会话自查——但要显式切换"对抗审查员"视角并注明该降级

子代理无状态、看不到本会话，任务里必须注入完整上下文：

```
角色：黑盒对抗审查员。把本次实现当作不可信交付物，目标是找出问题，不是确认正确。

上下文：
- 需求原文：<用户需求>
- 本轮改动摘要：<摘要>；git SHA：<sha>；版本号：<如有>
- 变更文件清单：<git show --stat 输出>
- 运行地址：<staging URL 或 localhost 实际地址>
- 验证方式：<如何登录/访问/触发被测功能>

任务：对照"需求"而非代码意图做黑盒验证：
1. 功能主路径是否达成需求
2. 边界/异常输入（空值、超长、并发、重复提交、非法参数）
3. 错误路径与降级表现
4. 安全面：XSS/注入/越权/敏感信息泄露/未鉴权端点
5. 回归：改动是否破坏相邻功能
6. 需求覆盖度逐条核对

能跑起来的就实际探测（curl / 脚本 / 行为级验证），不要只读代码下结论。

约束：只审查与报告——不修改任何文件、不提交、不部署。

输出格式：
- 问题清单：每条含 severity(critical/high/medium/low)、复现步骤、证据
- 需求覆盖度核对表（逐条 ✅/❌）——**每项必须附实测证据**（命令输出 / 响应内容 / 可观察行为描述），不接受"读过代码觉得对"；缺证据的项按 ❌ 计
- 完成度评分：0-100%（无 critical/high 且需求全覆盖 = 100%）
```

## 步骤 4：完成度判定

- 审查完成度 = 100%（无 critical/high、需求全覆盖）→ 进入步骤 5
- 否则：把问题归类为 bug / 覆盖缺口 / 设计偏差，给出新一轮修改方案，**回到步骤 1**
- 连续 2 轮在同一问题上无实质进展，或被外部因素（权限、环境、依赖服务）阻塞 → 停下来向用户汇报现状与选项，不要空转
- **迭代上限**：默认最多 8 轮（含首轮）。达到上限仍未 100% → 强制停下，输出当前迭代表格 + 遗留问题清单，由用户决定是否继续

## 步骤 5：清理与汇报

1. 清理本轮开发产生的无用产物：临时脚本、调试日志、探针/scratch 文件、随手建的测试数据。**只删本会话创建的文件**，删除前列出清单；不确定归属的列出来问用户。有归档价值的审查证据整理到项目约定的位置。
2. 确认 `git status` 干净（除有意保留的产物外）。
3. 输出最终汇报，包含：
   - 改了什么、为什么改（根因视角）
   - 部署状态：本地验证 / 已部署 staging（SHA + 地址）/ 待人工部署
   - 遗留问题与建议
   - 全部迭代表格记录：

```
| 迭代 | 版本号 | git SHA | 改动摘要 | 审查完成度 | 部署状态 |
|------|--------|---------|----------|------------|----------|
| 1    | 0.2.1  | ab0957c | …        | 72%（3 high） | staging |
| 2    | 0.2.2  | …       | …        | 100%       | 本地验证 |
```
